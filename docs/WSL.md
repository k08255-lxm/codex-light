# 在 Windows 桌面端使用 WSL Codex

> WSL 支持随 v0.4.6 发布。已在真实 Ubuntu WSL 2 中验证引擎发现、Linux Codex 技能管理和 Windows DSH 桌面宿主探测。各项验证范围见下文。

## 选择运行环境

1. Windows 桌面端仍需要 Windows Node.js 来运行界面后端。WSL 内的 Node 不代替这个依赖。
2. 从 v0.4.13 起，首次引导和打开「连接与运行」设置时，码舱会自动查询已注册的发行版，并只读检查正在运行的 WSL，不主动启动已知停止的发行版。如果发行版已停止、自动检测未确认，或 Codex 路径需要登录脚本，请选择“完整检测 WSL”。完整检测可能启动发行版；两种检测都不会执行 Codex 推理、登录或修改 Codex 配置。
3. 选择发行版，确认显示的默认 Linux 用户。必要时填写 Codex 的 **Linux 绝对路径**，例如 `/home/lee/.nvm/versions/node/v24.0.0/bin/codex`。不要填写 Windows 的 `codex.exe` 或 npm shim。
4. 保存后完全退出并重新打开码舱。保存选择不会切换或中断正在运行的会话；设置页分别显示当前环境与下次启动环境。
5. 要返回 Windows 原生 Codex，保存“Windows”并重新启动。

安装器未找到 Windows Codex 时可以选择稍后在应用中配置，而不强制另外安装一份 Windows CLI。Windows Node 检测和原有安装安全检查仍然保留。应用启动后，Codex 未找到或 WSL 不可用时仍可进入设置；不会偷偷切换到另一套账户。

## nvm、fnm 和自定义安装

自动检测使用非登录 shell，完整检测使用登录 shell；两者都会检查各自环境的 `PATH`。如果没有找到 Linux CLI，会检查标准 `~/.nvm/versions/node/*/bin` 和 `~/.local/share/fnm/node-versions/*/installation/bin`；仅在候选唯一时自动选择。

多个版本、仅交互式 shell 初始化可见的安装、自定义 fnm/nvm 位置，应明确指定 CLI 的 Linux 绝对路径。程序会只读核查 Linux 可执行文件或脚本及其 Linux Node，将所需 Node 目录用于该进程的 `PATH`，不会修改 shell 初始化文件。探测失败表示当前环境未能确定可用 CLI，**不等于未安装 Codex**。

发现过程不运行 `codex --version`。Windows 互操作挂载上的 npm shim、Windows `.exe/.cmd/.bat` 不会被当成 Linux CLI。

## 账户、路径和数据边界

- Codex app-server 在所选发行版默认用户下启动，使用该 Linux 用户的登录环境及 `CODEX_HOME`；不会复制 Windows 的登录文件、API key 或配置进入 WSL。
- 当前仅支持发行版默认用户，不能任意指定其他 Linux 用户。这保证执行身份与 Windows 的 WSL 文件共享身份一致。默认用户改变后需要重新发现并选择，旧选择不自动换用户继续运行。
- 码舱的项目列表、统计缓存和文件附件元数据按发行版、用户与 Linux Codex home 隔离。原 Windows 数据不迁移、不删除。
- Linux 项目在 Windows 界面中以 `\\wsl.localhost\发行版\…` 表示。选中的发行版内，路径保留大小写；其他发行版及普通网络共享不混入其路径映射。
- Windows 盘符路径通过所选发行版的 `wslpath` 转换，不假设挂载点一定是 `/mnt/c`。挂载配置、权限或沙盒不允许访问时会报错，不提升权限重试。
- 本地历史扫描限于所选 Linux Codex home。历史图片只读取原始记录和受信任引用，不为预览重新复制一份图片。
- 审批请求保留引擎原始路径及权限内容，避免路径转换改变授权含义。

## 功能范围与限制

WSL 模式下，模型、账户、聊天、历史、审批、插件配置及已在 WSL 内配置的 MCP 由所选 Linux app-server 处理；终端使用 Linux `/bin/sh`，不会把 Windows PowerShell 命令发给 Linux。已实测的项目与未覆盖的场景分别列在下方。

WSL 模式支持通过所选发行版的 Linux Git 读取仓库状态和文件差异；不会使用 Windows Git 解释 Linux 仓库路径。以下写入或升级操作仍由对应环境处理：

- Git 暂存、提交和推送。请在 WSL 终端操作；桌面面板提供只读状态和差异。
- Windows npm Codex 升级按钮。WSL 内 Codex 的升级需要在相应 Linux 环境处理。

DSH 桥不属于上述禁用项：可显式选择 Windows 或 WSL 原生桥；本地配置源编辑页仍不适用于 WSL。已有 MCP 不会被覆盖。具体边界见下方“DSH 环境选择”。

Linux 中无法安全映射到 Windows 文件系统语义的特殊文件名不会被强行转换。WSL 文件共享不可访问时，文件预览、文件夹选择和历史扫描可能不可用，即使引擎本身可以运行。

Windows 桌面端的项目入口和“连接与运行 → 工作目录”均可调用宿主文件夹选择器；设置页选择后先填入目录，点击保存才切换项目。所选发行版的目录可通过 `\\wsl.localhost\发行版\…` 访问。手机和普通浏览器页面不调用电脑的原生选择器，仍须使用已有项目或填写目录。

Android/网页远控不能更改宿主的 WSL 选择；它们连接的是桌面端当前运行环境。本功能不等于增加官方远控协议能力，也不保证官方仅在特定宿主开放的功能可在 WSL 使用。

## 已验证的范围

- 使用合成 app-server 测试 stdio 握手、请求路径往返、审批路径不变、进程退出和错误处理；没有调用真实模型。
- 测试发行版名称与路径校验、默认用户限制、Windows shim 拒绝、配置持久化、延迟到重启生效、原生功能禁用和鉴权。
- 测试 WSL 项目大小写、别名归一、历史图片原始 Linux 路径匹配，以及受信任本地链接范围。
- 在 Windows WSL 3.0.5.0、Ubuntu WSL 2 和 Linux Codex 0.171.0 上，码舱发现了默认用户和原生 CLI。使用隔离的 Linux Codex 配置目录和临时技能，实际完成了技能发现、停用、启用及强制刷新回读，验证了桌面 UNC 路径和 Linux 技能路径的往返转换。
- v0.4.13 的后台检测入口和停止状态处理已通过自动化测试；发布验收未在真实发行版上重跑此入口。实际 CLI 登录、真实历史加载不在上述 Ubuntu 实测范围内；切换引擎需重启，不支持在运行中热切换。

## DSH 环境选择

在连接设置中显式选择 DSH 所在环境。检测与生成计划不会修改 Codex 配置；点击确认连接后才创建本应用专属状态、专属 DSH profile，并通过带版本检查的 RPC 添加单个 MCP 条目。现有 MCP 配置一律保留，不自动替换。不能把保存注册当作连接成功，界面以实际 MCP 状态为准。

- **Windows DSH**：通过 WSL interop 和 stdio 连接，Windows 凭据留在 Windows，未开放网络监听或更改防火墙。只支持可往返映射为 Windows 盘符的项目；Linux `/home` 项目拒绝。工具执行环境及结果路径为 Windows。可通过认证本地完成队列唤醒码舱持有的同一父会话，失败仍可 `dsh_wait` 取回。
- **WSL 原生 DSH**：使用所选发行版默认用户的 Linux Node/DSH、供应商配置与凭据，支持 Linux 工作目录。不会导入 Windows 密钥。供应商来源或默认模型不明确时须先在 Linux 环境配置，不会擅自选择供应商。使用独立 `codecang-wsl` profile，不覆盖原 profile；支持同样的本地完成队列回调，`dsh_wait` 作为手动恢复方式。
- Windows 传给 WSL 的 `WSLENV` 被清空，以避免任意自定义密钥名跨账户传入；Linux 登录 shell 自己设置的环境保持有效。

已在真实 Ubuntu 中通过码舱的 Windows DSH 探测入口，核验 Windows 桌面 DSH 0.2.2-rc.3 的宿主身份、Node 24.21.0 和 SQLite 支持。使用隔离的 Linux Codex 配置完成注册与刷新后，在 Windows 盘符项目中通过 Linux Codex 的 `mcpServer/tool/call` 调用 `dsh_list` 和 `dsh_start` 成功。Windows DSH 接受了只读任务，工作目录映射正确。`dsh_wait` 将同一任务的最终错误 `TRANSPORT: Connection error.` 返回给 Linux Codex，本次没有收到模型回答。

### 本轮合成验证

- 已覆盖 DSH adapter、HTTP 模式绑定、连接服务、签名队列、回调恢复、账户隔离和安装身份。测试均使用合成数据，不代表真实 WSL 端到端验证。
- 新 bridge bundle 完整性、篡改拒绝、工具分发、鉴权与 stdio 合成测试通过；没有发出模型请求。
- 锁定的构建依赖安装遇权限限制；采用已安装、同 lock 哈希的 esbuild 0.25.12 只读复用，临时构建脚本仅替换构建器 import。此为替代构建验证，不宣称原构建脚本全流程运行通过。
- 开发阶段的 Windows 桌面编译通过（0 警告、0 错误）。WSL 原生 Linux DSH 和真实自动唤醒尚待验收。

## 自动唤醒的约束

完成队列使用每个运行环境独立的私有描述符与 HMAC，不建立网络监听、不连接默认 Codex daemon。只有本应用实际观察到的任务创建/续跑及明确 watch 才有授权；父对话、任务、轮次必须全部一致。父对话忙时延后，取消优先。投递前持久记录，结果不确定时不会自动重发，防止重复启动模型。

同一可识别 ChatGPT 账户重启后可恢复未投递的授权；账户改变则撤销。API-key 模式没有稳定的账户身份返回，因此只在本次运行自动唤醒，不跨重启重放旧 watch。未确认账户时暂停回调。旧桥不支持队列协议时拒绝启用，不退回其他 Codex 实例。

这些行为已用合成 RPC/队列测试，但尚未进行真实 WSL/Linux DSH 自动唤醒验收。

## 首次运行选择

已有用户保留当前环境，不重新弹出选择。新用户只有一个已经完整验证的可用引擎时自动采用；多个引擎则让用户选择；没有可用引擎时提供安装或配置入口。首次引导也会后台检测正在运行的 WSL；若同时发现 Windows 和 WSL Codex，仍需选择。自动检测不用登录脚本；完整检测需主动触发，可能启动停止的发行版。探测失败或超时属于未知，不能据此断言未安装或自动选择另一引擎。切换保存后需完全退出并重新打开应用，不热切换正在运行的任务。

自动唤醒的损坏占用记录、无法确认存活状态的进程或超出 32 次恢复记录链会停止自动接管，需人工检查；不会抢占或终止未知进程。此时可使用 `dsh_wait` 获取结果。
